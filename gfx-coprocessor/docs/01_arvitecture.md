# Графический сопроцессор для Z80: обзор архитектуры

*Черновик для обсуждения. Это не спецификация, а карта местности: что за блоки, как они связаны, что каждый делает. Цифры ориентировочные.*

## 1. Принципы

1. **Простота важнее пиковой скорости.** Узкое место всё равно память (около 27 МБ/с), поэтому ядро можно делать простым, лишь бы оно укладывалось в 8 тактов на пиксель.
2. **Ядро программируемое, а не жёстко-автоматное.** Регистровый файл в BRAM, один DSP, микропрограмма. Новый алгоритм означает новый микрокод, а не новую логику (нет комбинаторного взрыва).
3. **В железо выносится только горячий путь:** буферы слова и узкий комбайнер.
4. **Экранные координаты внутри, адреса снаружи не видны.** CPU говорит «нарисуй в (x, y)», а не «в адрес такой-то».
5. **Два формата пикселя: 4 и 8 bpp.** Формат 1 bpp допустим только как источник (шрифты, маски).
6. **Никакого аппаратного скроллинга.** Вместо него быстрое копирование блоков.
7. **Команды как записи в регистры:** RISC-стиль, всё тривиально по интерпретации.

## 2. Общая картина

![Архитектура сопроцессора](../output/architecture.svg)

*Где проходит граница доменов: **вся логика команд и регистров живёт в 8-битном домене**, где её проще минимизировать. **Ядро, буферы слов и видеоконтроллер** обращаются к памяти по 16 битам. Ядро по сути «мастер» на 16-битной шине, а в 8-битном домене оно видно только как набор регистров.*

*Пересечение доменов делается в одном месте: **регистры ядра**. CPU пишет туда по 8 бит, ядро читает по 24 бита.*

Особенность системы в том, что CPU записывает регистры GPU только через командный интерфейс. Но может прочитывать статус через прямой доступ к регистру. Также командный интерфейс не работает с регистрами палитры.

## 3. Блоки по порядку

### 3.1 Интерфейс к CPU

Четыре порта ввода-вывода (примерно):

| Порт | Назначение |
| --- | --- |
| CMD | запись в FIFO команд, 3 байта на команду |
| STATUS | чтение: FIFO заполнено, ядро занято, номер строки |
| PAL | запись палитры (индекс, затем цвет) |
| VRAM | окно в видеопамять с автоинкрементом (для загрузки данных) |

Команда уходит блоком `OTIR`: три байта на запись, примерно 50 мкс на пять-шесть команд. Если FIFO заполнено, выставляется `/WAIT` и CPU ждёт без опроса статуса.

### 3.2 FIFO и декодер команд

FIFO в BRAM, 512-1024 записей по 3 байта. Декодер берёт код команды и либо записывает операнд в регистр ядра, либо запускает микропрограмму. Пока ядро занято, команда, зависящая от результата, ждёт. Проще всего: **FIFO просто выдаёт команды по очереди, и `EXEC` блокирует выдачу до конца операции**.

### 3.3 Ядро

Микропрограммный автомат типа «маленький процессор»:

- **Регистровый файл** 32-64 слова по 24 бита (BRAM, два порта чтения).
- **АЛУ + один DSP-блок:** сложение, вычитание, сдвиги, сравнение, умножение 12×12.
- **Память микрокода** 256-512 слов, загружается процессором при старте.
- **Счётчики и переходы:** условия по знаку, нулю, переносу. Одна команда «цикл».

Регистры (наброски):

![Карта регистров](../output/register_map.svg)

| Группа | Регистры |
| --- | --- |
| Приёмник | DX, DY, W, H, D\_BASE, D\_STRIDE |
| Источник | SX, SY, S\_BASE, S\_STRIDE, S\_FMT |
| Аффинные шаги | A, B, C, D (3.12, со знаком) |
| Цвета | FG, BG, KEY |
| Операция | OP (код комбайнера), FLAGS |
| Клиппинг | CX0, CY0, CX1, CY1 |
| Временные | T0..T7, аккумуляторы |

### 3.4 Конвертер координат в адрес

Единственная точка, где вообще появляется адрес. Для линейного индекса `idx = y*stride + x`:

```
4 bpp:  слово = base + idx>>2,   пиксель в слове = idx[1:0]
8 bpp:  слово = base + idx>>1,   пиксель в слове = idx[0]
```

Умножение на каждый пиксель нужно только для аффинного режима и линий. Для прямоугольников микрокод считает индекс **один раз на строку**, а дальше просто делает `idx++`. Это оптимизация микрокода, а не железа.

### 3.5 Буферы слова

Память 16-битная, а ядро работает по одному пикселю, поэтому нужны два буфера:

- **Буфер источника:** держит последнее прочитанное слово.
- **Буфер приёмника:** держит слово, в котором меняем пиксели. Флаг «грязное».

Чтобы ядро не простаивало, чтение следующего слова запускается заранее.

### 3.6 Комбайнер

Узкий блок на пути данных: берёт пиксель источника, пиксель приёмника и регистры, выдаёт результат. 

В 4 bpp работает младшая тетрада, остальное маскируется. Таблица (LUT) не используется: в 8 bpp она слишком велика, а набор фиксированных операций работает в обоих режимах.

### 3.7 Источник: форматы 1, 4, 8 bpp

Канал источника имеет поле `S_FMT`:

| Формат | Читаем | Пиксель |
| --- | --- | --- |
| 8 bpp | байт | байт целиком |
| 4 bpp | тетрада | 4 бита |
| 1 bpp | бит | `бит ? FG : BG`, BG может быть «прозрачным» |

Это всё: stencil не отдельное устройство, а способ интерпретации слова. Одним и тем же приёмом получается рисование шрифтов и рисование контура через маску.

### 3.8 Клиппинг

Четыре регистра CX0, CY0, CX1, CY1 (знаковые 12 бит). Работа:

1. Перед циклом по строкам микрокод проверяет Y; строки вне окна пропускаются.
2. Для строки один раз обрезается диапазон X (начало и конец), цикл идёт только по видимому.
3. В аффинном режиме и в линиях проверка идёт на пиксель, а в прямоугольниках бесплатно.

### 3.9 Видеоконтроллер и палитра

Видеоконтроллер читает пакетами из памяти и отдаёт пиксели на палитру. Палитра лежит в 8-битном домене. Развёртка имеет **высший приоритет** в арбитре памяти.

## 4. Команды

Формат: **1 байт код + 16 бит операнд = 3 байта**. Любое 24-битное значение записывается двумя командами (`LO`, `HI`).

Запуск: команда `EXEC` блокирует выдачу следующих команд до конца операции.

![Опкоды команд и операций АЛУ](../output/operand_map.svg)

**Пример: нарисовать спрайт 16×16 с прозрачностью** (после одного раза настройки базы, строки и ключа):

```
SET_SX, SET_SY      ; откуда
SET_DX, SET_DY      ; куда
SET_W (=16), SET_H (=16)
EXEC  PROG_COPY
```

Пять-шесть команд, всё в одном `OTIR`.

## 5. Микрокод: как это выглядит

Микрослово (набросок, 24-32 бита): `[операция АЛУ | источник A | источник B | приёмник | управление памятью | переход]`.

![Формат микрослова](../output/microinstruction.svg)

Псевдокод микропрограммы **заливки прямоугольника** (без аффинных шагов):

```
PROG_FILL:
    clip_rect()                      ; обрезать DX, DY, W, H окном
    if W <= 0 or H <= 0: goto DONE
    row = H
ROW:
    idx = DY * D_STRIDE + DX         ; DSP: один раз на строку
    cnt = W
PIX:
    waddr, sub = split(idx)
    if waddr != cached_waddr:        ; смена слова
        flush_dst()
        dst_read(waddr)
    dst_word[sub] = combine(FG, dst_word[sub])
    idx++ ; cnt--
    if cnt != 0: goto PIX
    DY++ ; row--
    if row != 0: goto ROW
    flush_dst()
DONE: halt
```

В цикле `PIX` около 5-6 микроопераций. Это укладывается в бюджет 8 тактов на пиксель.

**Копирование спрайта** отличается добавлением второго индекса. **Аффинная версия:** индекс источника считается на каждый пиксель. **Линия (Bresenham):** сумматор ошибки плюс два шага, без умножения.

## 6. Бюджет

| Параметр | Оценка |
| --- | --- |
| Пропускная способность памяти | около 27 МБ/с |
| Развёртка 640×480×4 bpp | около 9,2 МБ/с |
| Остаётся ядру | 15-18 МБ/с |
| Копирование (читаем источник и приёмник, пишем) | порядка 10-15 Мпикс/с по памяти |
| Ядро при 6-8 тактах на пиксель (108 МГц) | 13-18 Мпикс/с |
| Z80 без помощи | 0,1-0,2 Мпикс/с |
| Весь экран 307 тыс. пикселей | порядка 25-30 мс |

Вывод: при таких цифрах ядро и память примерно сбалансированы. Доводить ядро до 1 такта на пиксель не имеет смысла.

## 7. Что мы осознанно не делаем

- Аппаратный скроллинг и page flip как обязательная вещь.
- LUT цвет×цвет.
- Форматы 2 и 3 bpp.
- Третий источник (заменяется двумя проходами через скрытую страницу).

## Принятые решения

- **Регистровый файл ядра:** 32 слова.
- **Микрокод в RAM (BRAM), не в ROM.** RAM дешевле и позволяет менять алгоритмы.
- **Порядок пикселей:** в байте первым (левым) идёт старшая тетрада.
- **Прозрачность:** цвет 0 источника никогда не пишется.
- **Комбайнер в два уровня.** Базовый: copy, AND, OR, XOR, сложение и вычитание с насыщением. Продвинутый: смешивание со сдвигом.
- **Запуск:** отдельная команда `EXEC`.
- **Переполнение FIFO:** шина просто не выдаёт ACK, пока в FIFO нет места.
- **Режим 8 bpp:** только 320×200.

## 8. Открытые вопросы

1. **Порядок байт в 16-битном слове:** какой байт идёт первым.
2. **Чтение-модификация-запись.** Принимаем ли чтение байта перед записью в 4 bpp?
3. **Заливка по целому слову** как отдельная ветка микрокода: нужна ли в первой версии?
4. **Ширина микрослова** и число микроопераций: определим на следующем шаге.
5. **Размер палитры** в режиме 4 bpp и 8 bpp: общая память или две отдельные.

## 9. Предлагаемый порядок работы

1. Договориться о картах регистров и командах.
2. Описать микрослово и набор микроопераций.
3. Написать на нём три эталонные программы.
4. Только после этого писать Verilog.
